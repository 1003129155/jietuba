## 结论

- **C++ 崩溃（P0）**：钉图右键菜单开着时按 Esc，C++ 版堆损坏崩溃（0xc0000374），复现 4/4。原因见下文「问题 1」。
- **原版问题，两边一致**：同一操作在 Python 里会连菜单带钉图一起关掉，不崩，但钉图丢了（问题 2）。按约定先修 Python，再同步 C++。
- 其余已测项两边一致，大多逐像素相同：所有标注工具画出的结果、长截图拼接、OCR 结果、扫码结果、保存的 PNG/PDF 字节数、各设置页（另列 3 处小差异）。
- 资源方面：连续截图 30 次，句柄、GDI、USER 对象数都不涨；C++ 全程私有内存比 Python 少约 70 MB。
- 自动化测不了、需要真鼠标或特殊环境的项列在最后。

## 发现的问题

1. **C++：钉图菜单开着时按 Esc 会崩溃。** `PinContextMenu::show` 把菜单放在栈上，父对象是钉图（`QMenu menu(parent)`，src/pin/pin_context_menu.cpp:25），钉图设了 `WA_DeleteOnClose`。Esc 先被钉图的普通模式快捷键处理器吃掉（日志里是「按键被 PinNormal 消费」），在菜单的 `exec` 循环里调用了 `close_unless_locked`。延迟删除在这个嵌套循环里执行，钉图析构时把栈上的菜单当作子对象 `delete`，于是 ntdll 报堆损坏。点菜单里的「关闭」项不会崩（菜单先退出，钉图在外层循环里才删除），直接在钉图上按 Esc 也不会崩。崩溃转储在 `%LOCALAPPDATA%\CrashDumps\jietuba_cpp.exe.{5456,42360,9256}.dmp`。fail-fast 不经过 C++ 的崩溃钩子，所以 faulthandler_cpp.log 里没有调用栈。
2. **原版：钉图菜单开着时按 Esc，菜单和钉图一起关掉。** 两边一致，150 ms 内钉图消失；点空白处关菜单时钉图保留。用户按 Esc 本意是关菜单。修 Python 时让钉图快捷键在有弹出菜单时不处理 Esc，C++ 同步后问题 1 的触发路径也会消失；C++ 的栈上菜单仍应改为不会被父对象删除的写法。
3. **C++：工具栏位置比原版偏右下 1 px**（截图工具栏和「…」弹层；选区和信息条位置一致）。
4. **C++：「截图设定 > OCR 设置」的两个选择按钮比原版宽 24 px**（右边对齐，同页其他按钮宽度一致）。
5. **C++：整数工具设置写回注册表时是 REG_QWORD**（原版 REG_DWORD），例如 `tools\text\background_opacity`。数值不变，但共用设置被 C++ 写过之后类型会变。来源是 `ToolSettingsManager` 把整数统一转成 `qint64`。
6. **两边一致：钉图缩略图还原后位置偏左上 1 px**（328,251 → 327,250），原版行为。
7. 测试本身的副作用：「截图完成时自动保存」默认开启、默认目录是用户的图片目录，前几次运行存进去 6 张图，已移到测试临时目录；后续运行改为临时保存目录。
